#### #0108 | S2 | vendored libbw64 is patched, but its provenance record says "verbatim"
- **Evidence**: `Sources/ThirdParty/libbw64/UPSTREAM.md` states "Local modifications | none — the
  headers are vendored verbatim" and cites `bw64/version.hpp`, build date 2019-01-21. Verified
  against the upstream tag `0.10.0` (`ebu/libbw64`, commit `3a43f909f7e8f6bef93403816e9b73b8bfa5a133`)
  by hashing every header:
  - `parser.hpp`, `chunks.hpp`, `reader.hpp`, `utils.hpp` — **identical**;
  - `bw64/writer.hpp` and `bw64/bw64.hpp` — **differ**, one line each:
    `uint16_t sampleRate` → `uint32_t sampleRate` in the `Bw64Writer` constructor and in `writeFile`;
  - `LICENSE` — identical (`c71d239d…d0ab4`);
  - `bw64/version.hpp` — **does not exist upstream**; upstream takes the version from
    `project(libbw64 VERSION 0.10.0)` in `CMakeLists.txt`, so this is a locally authored file.
- **Why it matters**: the patch itself is correct and useful — upstream's `FormatInfoChunk` already
  stores `uint32_t sampleRate` (`chunks.hpp:120,182`), so the public writer API was truncating it;
  `Sources/BW64Bridge/bw64_bridge.cpp:209-215` passes a `std::uint32_t` through. But an auditor
  cannot reproduce the vendored tree from the recorded provenance, and the next upstream refresh
  would silently drop the fix. For a supply-chain-sensitive artefact this is a real integrity gap,
  not a typo.
- **Fix**: replace the "Local modifications: none" row with an explicit list (file, hunk, reason,
  and the upstream type mismatch that motivates it), state that `version.hpp` is locally authored
  and which upstream metadata it mirrors, and add the upstream commit SHA. Keep the patch minimal
  and add a short "how to refresh" that reapplies it.
- **Host**: local (documentation + optional `bw64.patch` file).

#### #0113 | S0 | an image action can overwrite the user's own source artwork
- **Evidence**: `Sources/converter/ImagePipeline.swift:130` `let prefix = deliveryPrefix ?? imagePrefix(from: source.stem)`;
  `:138` `let output = cli.outDir.appendingPathComponent("\(prefix)_\(target.label)").appendingPathExtension("png")`;
  `:140` reuse check, `:168` `try publishTemp(temp, to: output)`.
  `imagePrefix` (`ValidationPipeline.swift:1207-1210`) strips a trailing derivative label unless
  `--keep-full-name` is set (`stripTrailingDerivedImageSuffix`, `:1191-1199`, strips `_8K`, `_4K`, …).
  The audio side has exactly the guard the image side lacks: `AudioPipeline.swift:1603-1607`
  `requireDistinctOutput(_:from:)` "Refusing to write … over its own source".
- **Why it matters**: with the default `keepFullName = false`, `converter -aipix` on `Artwork_8K.png`
  computes `prefix = "Artwork"` and therefore `output == source`. The reuse verifier fails when the
  file's dimensions are not exactly the 8K target, the file is re-rendered, and `publishTemp`
  replaces the original; its backup is deleted on success (`PipelineCore.swift:594-596`), so the
  user's master is gone. A 8192×4320 DCI master named `Master_8K.png` loses 256 px per side; a
  1920×1080 file named `Cover_8K.png` is upscaled over itself. `-runpix` and `-short` reach the same
  function (`Actions.swift:423,529,817`).
- **Fix**: refuse an output whose standardized path equals the source, mirroring
  `requireDistinctOutput`, in `aipixFile` (and `squarePNGFrom8K`/`nftFrom8K` for symmetry).
- **Test**: `-aipix` on `<stem>_8K.png` with non-target dimensions must throw and leave the source's
  CRC32 unchanged (fails today).
- **Host**: local.

#### #0114 | S2 | the configured delivery QC ceilings never gate the delivered files
- **Evidence**: every deliverable verify call passes `qcPolicy: nil` — `AudioPipeline.swift:1675,1687`
  (M4A), `:1708,1720` (MP3), `:1738` (FLAC), `:1616,1649` (standard WAV), and
  `Actions.swift:698,727,908,921,1349` (main 8K MP4, album MP4, `-m4atomp4`). The policy that is
  built from the `AUDIO_QC_*` keys, `config.deliveryAudioQCPolicy`
  (`QualityReporting.swift:88-98`, keys validated at `Config.swift:365-381`), is used **only** to
  measure metrics for a drift comparison (`ValidationPipeline.swift:962-963`), never passed into
  `verifyAudioQC` (`ValidationPipeline.swift:390`, reached only when `qcPolicy != nil`,
  `:770-771`). Non-nil policies exist only for the short-form path (`Actions.swift:733,962`)
  and mastering (`AudioPipeline.swift:715`).
- **Why it matters**: the ceilings the operator sets — `AUDIO_QC_MAX_CLIPPED_SAMPLES=0`,
  `AUDIO_QC_MAX_TRUE_PEAK_DBTP=-1.0`, `AUDIO_QC_MAX_DC_OFFSET`, `AUDIO_QC_MAX_STEREO_IMBALANCE_DB` —
  are validated at load and then never evaluated for the M4A/MP3/FLAC/WAV/MP4 deliverables. A hot
  master whose AAC/MP3 encode adds inter-sample clipping changes integrated loudness by a few
  tenths of a dB, so the 1 dB drift check and the audibility check both pass and the file is
  published. A configured check that can never fire is exactly the §5 failure mode.
- **Fix**: pass a rebased `config.deliveryAudioQCPolicy` (via `loudnessPreservingQCPolicy` where the
  step legitimately changes loudness) into the deliverable verify calls, starting with the lossy
  encode sites.
- **Test**: an encode whose QC metrics breach a ceiling must fail the run; today it publishes.
- **Host**: local.

#### #0115 | S2 | a failed loudness QC is published with a warning, not an error
- **Evidence**: `AudioPipeline.swift:672-680` — when `result.passed` is false the code falls through
  to `loudnessCandidateIsPublishableFallback(...)`, and if that returns true it runs
  `try publishTemp(temp, to: output)` and only `logger.warn("Created \(reason) loudness media without
  compression: …")`. The fallback gate (`:347`) drops the integrated-loudness and true-peak issues
  before judging the rest, and its final bound is `:368`
  `abs(integratedLUFS - policy.targetLUFS) <= max(policy.lufsTolerance, 6.0)` — while the action's own
  tolerance is 0.8 LUFS (`:307`). The album path repeats the pattern (`:2240`).
- **Why it matters**: `-loudness` on a source whose static-gain plan under-applies publishes a file
  up to 6 LUFS off the requested target, labels it "closest-safe"/"peak-constrained"
  (`:384-386`), exits 0, and reports success. The run's only signal is one WARN line.
- **Fix**: keep the fallback but make it visible and bounded — require `--allow-unverified-loudness`
  for the >tolerance case, or record the fallback in the run summary so a scripted caller can fail
  on it.
- **Test**: a render 3 LUFS off target must not exit 0 without an explicit opt-in.
- **Host**: local.

#### #0116 | S2 | the success path drains child pipes without a deadline
- **Evidence**: `ProcessRunner.swift:273-274` `stdout: stdoutCapture.waitString(),` / `stderr: …` →
  `:49-52` `waitString()` → `group.wait()` with no deadline. The timeout path deliberately avoids
  this and says so: `:227-229` "do not block on pipe EOF, which a grandchild that inherited the pipe
  could postpone", using `waitString(until: deadline)` (`:230`). The watchdog is already cancelled by
  then (`:252-254`).
- **Why it matters**: a child that exits 0 while leaving a grandchild holding the inherited stdout or
  stderr write end (wrapper scripts, `sh -c 'tool &'`, delegate processes) blocks `makeResult`
  forever — the CLI never returns although the command finished, and no timeout can rescue it.
- **Fix**: use a bounded drain on the success path too (`waitString(until:)` with a drain deadline)
  and report a partial-output diagnostic if it is hit.
- **Test**: a fake tool that forks a pipe-holding grandchild and exits 0 must return within the
  drain deadline instead of hanging the suite.
- **Host**: local.

#### #0117 | S2 | cancelling one operation kills unrelated concurrent children
- **Evidence**: `PipelineCore.swift:492-493` `} onCancel: {` / `runner.terminateActiveProcesses()`;
  `ProcessRunner.swift:145-149` iterates the whole `activeProcesses` list; the justification at
  `:143-144` assumes "Every child this runner launched belongs to the work being cancelled". One
  runner is shared for the whole run (`Main.swift:39`), and the pipeline runs independent branches
  concurrently (`Actions.swift:687-688` `async let imageArtifactsTask` / `async let audioArtifactsTask`;
  `:644-646` `async let m4aTask` / `async let mp3Task`), with `total = 2…4` permits
  (`Support.swift:88-100`).
- **Why it matters**: when one `async let` sibling fails, Swift cancels the other; its cancellation
  handler now SIGTERMs every live ffmpeg/magick child, including jobs of branches that are neither
  cancelled nor doomed. The victim's `ProcessRunner` sees `terminationStatus == 15`, `Task.isCancelled`
  is false (`:260`), so it reports `Command failed: … killed by signal 15 (SIGTERM)` (`:285`) — a
  misleading cause for an unrelated file's failure.
- **Fix**: scope the kill set to the cancelling operation (a per-permit token/box passed to `run`,
  or one `activeProcesses` set per fan-out scope).
- **Test**: cancel one fan-out branch and assert the sibling's ffmpeg still completes and its output
  is produced.
- **Host**: local.

#### #0121 | S2 | `--sleep-seconds` accepts negative and effectively unbounded values
- **Evidence**: `CLI.swift:282-286` accepts any finite `Double`; the consumer `PipelineCore.swift:669-670`
